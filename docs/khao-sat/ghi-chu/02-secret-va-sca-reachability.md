# Secret-leak detection and SCA with reachability / exploitability analysis in company CI (2022–2026)

Scope note: 21 tool calls (searches and abstract/HTML fetches). Most numbers come from arXiv abstracts or HTML pages. Where only a search snippet supported a claim, it is marked "(snippet only)". I did not independently verify the seed paper arXiv:2609.15425.

## Q1. SCA: tool disagreement, false positives from unreachable code, reachability methods, VEX, and LLM-assisted exploitability judgment. How much alert reduction is reported?

### Takeaway
SCA tools disagree heavily, mainly because they use different vulnerability databases. Package-level alerts overstate real exposure by roughly 1 to 2 orders of magnitude: in Maven, about 1.2% of transitively affected projects actually call the vulnerable code, and VAScanner finds 21.5% of projects using vulnerable libraries are actually threatened. Open-source reachability tooling exists but is uneven. It is mature for Go (govulncheck), experimental for Rust and JAR in OSV-Scanner, and mostly commercial for Java/JS/Python. The newest benchmark (VEX-Bench, Sep 2026) finds that SCA tools reach only about 22–29% precision, that static reachability barely helps, and that LLM agents reach about 82–89% status accuracy at $0.03–$1.08 per case.

### Cited Findings

**Tool disagreement (SCA / container scanners / VEX)**
- Imtiaz, Thorn, Williams, "A Comparative Study of Vulnerability Reporting by Software Composition Analysis Tools," ESEM 2021, arXiv:2108.12078. They ran 9 SCA tools on OpenMRS (Maven + npm). Reported vulnerable dependencies ranged from 17 to 332 (Maven) and 32 to 239 (npm). Unique known vulnerabilities ranged from 36 to 313 (Maven) and 45 to 234 (npm). The accuracy of each tool's vulnerability database was the key differentiator. The authors recommend not relying on any single tool and call for false-positive metrics. — [arXiv 2108.12078](https://arxiv.org/abs/2108.12078); [ESEM 2021 page](https://conf.researchr.org/details/esem-2021/esem-2021-technical-papers/4/A-comparative-study-of-vulnerability-reporting-by-software-composition-analysis-tools)
- "Deciphering Discrepancies: A Comparative Analysis of Docker Image Security," SCAM 2024 (NIER track). On 927 Docker images (865 with vulnerabilities), Trivy and Grype disagreed on both the number and the IDs of vulnerabilities. The PNNL listing is dated 2025, so check the year before citing. (snippet only) — [SCAM 2024](https://conf.researchr.org/details/scam-2024/scam-2024-new-ideas-and-emerging-results/3/Deciphering-Discrepancies-A-Comparative-Analysis-of-Docker-Image-Security); [PNNL](https://www.pnnl.gov/publications/deciphering-discrepancies-comparative-analysis-docker-image-security)
- Churakova, Ekstedt, Schmid, "Vexed by VEX tools: Consistency evaluation of container vulnerability scanners," arXiv:2503.14388 (v3, Mar 2026; no venue listed). It evaluates 7 VEX-generating tools (Trivy, Grype, OWASP DepScan, Docker Scout, Snyk, OSV, Vexy) on 3 container-image datasets using Jaccard/Tversky similarity. Consistency is low, the databases queried have the largest impact, and the authors read this as "low maturity" of the VEX tool space. Secondary coverage reports Trivy marking 7,767 vulnerabilities as affected versus 1,266 for Docker Scout on one subset; this figure is unverified from the primary source. — [arXiv 2503.14388](https://arxiv.org/abs/2503.14388)
- Practitioner anecdote, not peer-reviewed: Grype output differed by 66% depending on whether the SBOM was generated by Syft or by Trivy. — reported in search results; treat as unverified (no stable primary URL captured).

**Package-level vs code-level (reachability) exposure: how much noise**
- Mir, Keshani, Proksch, "On the Effect of Transitivity and Granularity on Vulnerability Propagation in the Maven Ecosystem," SANER 2023, arXiv:2301.07972. The study covers about 3M Maven packages with whole-program call graphs. Of 1.1M vulnerable projects, only 31% have the vulnerability in a direct dependency. Only 1.2% of transitively affected projects actually use the vulnerable code, and the abstract says fewer than 1% have a reachable call path. Callable-level analysis is a lower bound, and the authors still recommend considering transitive dependencies. Dataset: Zenodo doi 10.5281/zenodo.7540492. — [arXiv 2301.07972](https://arxiv.org/abs/2301.07972v1); [TU Delft](https://repository.tudelft.nl/record/uuid:600fd3dc-9069-48e6-8911-f4cd2253e714)
- Zhang, Fan, Chen, Cai, Xu, Zhao, "Does the Vulnerability Threaten Our Projects? Automated Vulnerable API Detection for Third-Party Libraries" (VAScanner), arXiv:2409.02753, Sep 2024. arXiv lists a related TSE DOI, but the venue is unconfirmed. The approach extracts patch methods from fix commits, finds root methods, and runs backward call-graph analysis to get vulnerable APIs. The database covers 90,749 vulnerable APIs (2,410,779 counted with versions) across 362 TPLs and 14,775 versions, with a 1.45% false-positive proportion. In 3,147 Java projects that use vulnerable libraries, only 21.51% are actually threatened through vulnerable APIs. VAScanner outperforms Eclipse Steady on direct dependencies. The paper notes that commercial SCA tools offer reachability but there are "no open-source alternatives" for evaluation. — [arXiv 2409.02753](https://arxiv.org/abs/2409.02753)
- Ponta, Plate, Sabetta, "Detection, assessment and mitigation of vulnerabilities in open source dependencies," Empirical Software Engineering 25:3175–3215 (2020), DOI 10.1007/s10664-020-09830-x. Eclipse Steady (formerly SAP Vulas) does code-centric, usage-based detection with static and dynamic reachability. It was evaluated on 300 SAP enterprise applications with 78,165 dependencies, compared with OWASP Dependency-Check, and is the recommended Java scanner at SAP. Open-sourced in Oct 2018 under Apache-2.0, it is an Eclipse incubator project. This is pre-2022 but is the canonical baseline. — [DOI](https://doi.org/10.1007/s10664-020-09830-x); [GitHub eclipse-steady](https://github.com/eclipse-steady/steady); [project page](https://eclipse-steady.github.io/steady/about)
- Foo et al. (Veracode), "The Dynamics of Software Composition Analysis," arXiv:1909.00973 (2019). Static call graphs introduce both false positives and false negatives in reachability. They propose combining static and dynamic call graphs. This is older background. — [arXiv 1909.00973](https://arxiv.org/pdf/1909.00973)
- "Determining the Unreachable: Constraint-Guided Reachability Analysis for Dependency Vulnerabilities" (ConVReach), ACM DOI 10.1145/3798255. It targets static paths that look reachable but are infeasible, using constraint/statistical reasoning. In the authors' comparison, ConVReach and dynamic methods produced no false positives. The venue (likely TOSEM) and authors are unverified (snippet only). — [ACM DL](https://dl.acm.org/doi/10.1145/3798255)
- "Cross-Ecosystem Vulnerability Analysis for Python Applications," arXiv:2603.18693 (2026). It stitches Python and native-binary call graphs to check whether vulnerable native symbols are reachable from Python code. It reports a "significant" false-positive reduction compared with a baseline that ignores OS package versions and backports; no exact number was captured. (snippet only) — [arXiv 2603.18693](https://arxiv.org/html/2603.18693v1)

**LLM / agent-based exploitability (VEX) judgment, 2025–2026**
- Shi, Tsien, Di, ..., Zhang (Purdue + Red Hat), "VEX-Bench: Benchmarking LLM Agents for Assessing Exploitability of Software Supply Chain Vulnerabilities," arXiv:2609.08040v1, 7 Sep 2026, no venue stated. This is the most directly relevant paper. — [arXiv 2609.08040](https://arxiv.org/html/2609.08040)
  - Benchmark: 75 cases, 67 CVEs, 35 repositories. Java has 25 cases (10 projects), Go 30 (15), Python 20 (10); there is no JS/npm. Five annotators labeled the cases, with Fleiss' kappa 0.667 on calibration and 88.3% of labels confirmed in review. 29.3% of cases are affected and 70.7% not affected; 38 cases are code_not_reachable. Labels follow VEX status plus justification categories.
  - Baselines on the full set (n=75): OSV-Scanner had precision 27.4%, recall 77.3%, F1 40.5%. Trivy had precision 26.0%, recall 59.1%, F1 36.1%.
  - Go subset (n=30): OSV detection-only had precision 24.1%, recall 100%. OSV with reachability had precision 28.6%, recall 85.7%, F1 42.9%. govulncheck had precision 22.2%, recall 28.6%, F1 25.0%, and completed only 19 of 30 cases. 70% of the tools' false positives are still labeled code_not_reachable.
  - Agents, binary status accuracy (mean of 3 runs):
    - Claude Opus 4.6 (Claude Code): 88.4%, $0.595/case
    - GPT-5.5 (Codex): 89.3%, $1.082/case
    - DeepSeek-V4-Pro: 84.0%, $0.075/case
    - GLM-5.1: 84.4%, $0.095/case
    - DeepSeek-V4-Flash: 72.9%, $0.027/case
  - Only GPT-5.5 exceeds 70% macro-F1 on fine-grained justification (73.5%). Python is the hardest language (justification macro-F1 56.5%) and Go the easiest (75.5%).
  - Limitations: small scale, single gold label, and static repository-level evidence that cannot capture deployment context.
- "Sifting the Noise: A Comparative Study of LLM Agents in Vulnerability False Positive Filtering," arXiv:2601.22952. It covers SAST, not SCA, with Aider, OpenHands and SWE-agent. On the OWASP Benchmark, the false-positive rate fell from over 92% to as low as 6.3%. On an OSS-Fuzz set, SWE-agent with Claude Sonnet 4 identified 95.5% of false positives at 95.5% precision, versus 36.4% for vanilla prompting. Agents sometimes suppress true positives. — [arXiv 2601.22952](https://arxiv.org/abs/2601.22952)
- OpenAnt, arXiv:2606.19149. This is LLM vulnerability discovery, not SCA. A static reachability prefilter removes 83–99% of functions, e.g., 64,132 down to 2,281 in one repo (96.4%). It is useful only as evidence of the "reachability first, then LLM" pattern. — [arXiv 2606.19149](https://arxiv.org/html/2606.19149v2)

**Vendor claims (not peer-reviewed; marketing)**
- Semgrep Supply Chain claims dataflow reachability across 10 languages cuts noise from false positives "by as much as 98%" (Dec 2024 blog, an "up to" figure). — [Semgrep blog](https://semgrep.dev/blog/2024/semgrep-supply-chain-announces-dataflow-reachability-support-for-10-languages)
- Endor Labs markets reachability-driven SCA, but I captured no verified primary percentage. — [Endor Labs page](https://www.endorlabs.com/learn/best-sca-solutions)

### Inferences
- The research consensus is clear. Package-level SCA has about 20–30% precision against exploitability ground truth (VEX-Bench). Code-level analysis shows that only about 1–22% of flagged projects actually reach vulnerable code (Mir 2023: 1.2%; VAScanner: 21.5%). Reported reductions therefore range from about 78% (VAScanner) to about 98% (Mir; Semgrep's vendor claim). Expect large variance by ecosystem and by how the vulnerable function is identified.
- The bottleneck is no longer "can we build call graphs". It is three things: mapping CVEs to vulnerable functions (a symbol database), handling dynamic features (reflection, interfaces, Python dynamism), and producing justifications that humans or VEX consumers trust. VEX-Bench shows static reachability alone (OSV, govulncheck) adds little precision, while agents add much more at low cost.
- For a 3-week course project, a feasible publishable angle is a company-internal replication of the VEX-Bench pipeline: SCA alerts → reachability prefilter → LLM agent producing an OpenVEX status and justification → developer validation. The headline metric would be the reduction in actionable alerts per repo, with recall checked on a labeled sample. The cheap open models in VEX-Bench (DeepSeek-V4-Pro at $0.075/case) make this affordable.

### Gaps
- I did not verify the Elder et al. paper "Do I really need all this work to find vulnerabilities?" (believed EMSE 2022, comparing SAST/DAST/manual techniques on a Java app); it is not SCA-specific.
- I did not find an independent peer-reviewed measurement of Snyk, Endor Labs, or Semgrep reachability accuracy. VEX-Bench evaluates only OSV-Scanner, Trivy and govulncheck.
- I found no peer-reviewed 2023–2024 study that includes OSV-Scanner alongside Trivy and Grype on application (non-container) projects. The seed paper (arXiv:2609.15425) may be the only one, and it is unverified here.
- I did not confirm the current maintenance status of Eclipse Steady. It was historically active, but recent commit activity is unknown.
- The ConVReach venue and authors, and the arXiv:2603.18693 numbers, are unverified.

## Q2. Secrets: benchmarks, comparative tool studies (precision/recall), and LLM-based detection / false-positive filtering

### Takeaway
SecretBench (MSR 2023) is the standard ground-truth dataset: 97,479 labeled candidates, of which 15,084 are true secrets, from 818 repos. On it, the best regex tools have poor precision: GitHub Secret Scanning 75%, Gitleaks 46%, while Gitleaks has the best recall at 88%. LLM-based second-stage classifiers report F1 around 0.98 on SecretBench-derived splits. However, a 2026 paper shows that duplication in the benchmark inflates these scores, so in-company validation matters. GitHub reports up to 94% false-positive reduction with Copilot secret scanning.

### Cited Findings
- Basak, Neil, Reaves, Williams, "SecretBench: A Dataset of Software Secrets," MSR 2023 Data & Tool Showcase, arXiv:2303.06729. It has 97,479 labeled secrets, of which 15,084 are true secrets, from 818 public GitHub repos, covering 49 languages and 311 file types. Dataset access terms are not stated on the abstract page; I believe it is available on request from the authors, but this is unverified. — [arXiv 2303.06729](https://arxiv.org/abs/2303.06729)
- Basak, Cox, Reaves, Williams, "A Comparative Study of Software Secrets Reporting by Secret Detection Tools," ESEM 2023, arXiv:2307.00714. It evaluates 5 open-source and 4 proprietary tools on SecretBench.
  - Precision: GitHub Secret Scanner 75%, Gitleaks 46%, "Commercial X" 25%.
  - Recall: Gitleaks 88%, SpectralOps 67%, TruffleHog 52%.
  - False positives come from generic regexes and weak entropy calculation. False negatives come from faulty regexes, skipped file types, and incomplete rulesets.
  - Recommendations: choose tools by the secret types present, update rules regularly, and use verification correctly.
  - [arXiv 2307.00714](https://arxiv.org/abs/2307.00714); [ESEM 2023](https://conf.researchr.org/details/esem-2023/esem-2023-technical-track/7/A-Comparative-Study-of-Software-Secrets-Reporting-by-Secret-Detection-Tools)
- Rahman, Ahmed, Wahab, Sohan, Shahriyar, "Secret Breach Detection in Source Code with Large Language Models," ESEM 2025, arXiv:2504.18784. The pipeline is regex candidate extraction followed by LLM classification, using the 818-repo benchmark (SecretBench). Fine-tuned LLaMA-3.1 8B reached binary F1 0.9852, outperforming regex-only baselines. Mistral-7B reached multiclass accuracy 0.982. Per-tool baseline numbers were not on the abstract page. — [arXiv 2504.18784](https://arxiv.org/abs/2504.18784)
- "Secret Leak Detection in Software Issue Reports using LLMs: A Comprehensive Evaluation" (earlier title "Secret Breach Prevention in Software Issue Reports"), arXiv:2410.23657 (v4). It applies the same regex-then-LLM pattern to GitHub issue reports, where dummy or placeholder credentials are correctly ignored. I did not capture the numbers. — [arXiv 2410.23657](https://arxiv.org/html/2410.23657v4)
- Biringa and Kul, "Detecting Hard-Coded Credentials in Software Repositories via LLMs," ACM Digital Threats 6(3), July 2025, DOI 10.1145/3744756, arXiv:2506.13090. It feeds LLM embeddings into a DL classifier. It notes that earlier ML filters (a voting classifier at 84% precision / 89% recall over 300 GitHub repos) struggle with contextual sequences. (Venue per search snippet.) — [arXiv 2506.13090](https://arxiv.org/abs/2506.13090); [ACM DL](https://dl.acm.org/doi/10.1145/3744756)
- Saha et al., "Secrets in Source Code: Reducing False Positives Using Machine Learning" (COMSNETS 2020, pre-2022). Regex plus ML with a soft voting classifier reached F1 86.7%, as reported secondhand. (snippet only)
- Soltaniani and Ghafari, "From Data Leak to Secret Misses: The Impact of Data Leakage on Secret Detection Models," arXiv:2601.22946, Jan 2026. Duplicate or near-duplicate samples across train/test splits in a widely used hard-coded-secrets benchmark (SecretBench, per search snippets) inflate the reported performance of AI detectors, which were tested as Random Forest, LSTM, and GraphCodeBERT. The abstract gives no numbers. — [arXiv 2601.22946](https://arxiv.org/abs/2601.22946)
- "Checked-In Secret Detection: Strings are All You Need," ISSTA 2026 (Oct 4–9, 2026, Oakland). StringGroup context extraction keeps about one third of the context while retaining over 80% of the semantic information. The Secretron Transformer detector found 48 previously unknown secret keys in 26 real applications. — [ISSTA 2026](https://conf.researchr.org/details/issta-2026/issta-2026-research-papers/116/Checked-In-Secret-Detection-Strings-are-All-You-Need)
- Li et al., "Automatically Detecting Checked-In Secrets in Android Apps: How Far Are We?", arXiv:2412.10922. This is an empirical study of secret detectors on Android apps; I did not capture the numbers. — [arXiv 2412.10922](https://arxiv.org/abs/2412.10922v2)
- A 2026 Springer EMSE paper titled "Learning to detect hardcoded secrets" (DOI 10.1007/s10664-026-10929-w) appeared in one search. The snippet reports 1,495 false positives versus 68 false negatives, over-reliance on variable names, and "an off-the-shelf LLM provides comparable results". A follow-up search could not confirm the authors or venue details, so treat it as unverified. — [Springer link](https://link.springer.com/article/10.1007/s10664-026-10929-w)
- GitHub engineering, "Finding leaked passwords with AI: How we built Copilot secret scanning" (GA in Oct 2024). It reports "in some cases" a 94% reduction in false positives across organizations, a best-case figure. GitHub docs caveats:
  - Generic-secret detection may produce more false positives than partner patterns.
  - Fake, test, or low-entropy passwords are skipped.
  - At most 100 passwords are detected per push.
  - Alerts stop for a file after 5 or more secrets in it are marked false positive.
  - [GitHub blog](https://github.blog/engineering/platform-security/finding-leaked-passwords-with-ai-how-we-built-copilot-secret-scanning/); [GitHub docs](https://docs.github.com/en/enterprise-cloud@latest/code-security/responsible-use/responsible-ai-generic-secrets)

### Inferences
- Gitleaks has high recall and low precision (46%). That makes it a natural candidate generator. An LLM or verifier second stage (TruffleHog-style live verification, or an LLM classifier) is the published recipe for raising precision.
- Because of SecretBench leakage (Soltaniani & Ghafari 2026), F1 ≈ 0.98 claims probably overstate real-world performance. A company deployment that measures precision on fresh internal repos, de-duplicated by fingerprint as in the seed paper, would be a genuine contribution.
- Secrets work is lower-risk for a 3-week project than reachability. Labeling a secret candidate takes seconds, while labeling CVE exploitability takes minutes to hours (VEX-Bench needed 5 expert annotators for 75 cases).

### Gaps
- I did not find the Basak et al. paper "What are the Practices for Secret Management in Software Artifacts?" (believed SecDev 2022, arXiv 2208.11280). This is unverified and was not fetched.
- I found no peer-reviewed head-to-head of current Gitleaks v8 vs TruffleHog v3 (with verification) vs detect-secrets vs GitHub Copilot secret scanning on the same 2025–2026 data. The ESEM 2023 numbers predate the LLM features.
- No per-tool baseline precision from Rahman et al. 2025 was captured.

## Q3. Open gaps a small team could address in ~3 weeks with measurable company effect; open datasets and ground truth

### Takeaway
The clearest open gap is validating LLM-plus-reachability exploitability triage, and LLM secret filtering, on real company code with developer-confirmed ground truth. Existing benchmarks are small (VEX-Bench: 75 cases, no JS), public-only, or leakage-prone (SecretBench).

### Cited Findings
- VEX-Bench authors' stated open problems:
  - small scale;
  - no JavaScript/npm;
  - only four not-affected justification categories;
  - a single gold label per case;
  - static evidence that cannot capture deployment context;
  - agents' difficulty moving from binary status to justification, the "central open challenge".
  - [arXiv 2609.08040](https://arxiv.org/html/2609.08040)
- Imtiaz et al. call for false-positive metrics for SCA tools and for continuous monitoring of vulnerability data. — [arXiv 2108.12078](https://arxiv.org/abs/2108.12078)
- VAScanner notes a lack of open-source reachability alternatives for Java, which hampers evaluation. — [arXiv 2409.02753](https://arxiv.org/abs/2409.02753)
- Several VEX tools disagree strongly, and the VEX tool space has "low maturity". — [arXiv 2503.14388](https://arxiv.org/abs/2503.14388)
- SecretBench data leakage inflates ML/LLM detector results. — [arXiv 2601.22946](https://arxiv.org/abs/2601.22946)
- Available ground truth:
  - SecretBench: 97,479 labeled candidates, 15,084 true secrets. — [arXiv 2303.06729](https://arxiv.org/abs/2303.06729)
  - VEX-Bench: 75 labeled CVE/repo cases in Java, Go and Python. — [arXiv 2609.08040](https://arxiv.org/html/2609.08040)
  - Mir et al. Maven reachability dataset on Zenodo, doi 10.5281/zenodo.7540492. — [arXiv 2301.07972](https://arxiv.org/abs/2301.07972v1)
  - VAScanner vulnerable-API database: 90,749 APIs. Its public release status is unverified. — [arXiv 2409.02753](https://arxiv.org/abs/2409.02753)

### Inferences
These are proposals, not findings. Candidate 3-week contributions at company Z:
1. **SCA triage funnel study.** Run Syft + Grype/Trivy/OSV-Scanner, deduplicate by fingerprint, apply a reachability filter (govulncheck/OSV for Go; Semgrep CE or VAScanner-style symbol matching for Java/Python where feasible), then an LLM agent that emits an OpenVEX status and justification. Metrics:
   - alerts per repo at each stage, i.e., percent reduction;
   - recall on a developer-labeled sample of about 50–100 alerts;
   - minutes of triage per alert;
   - developer acceptance (Likert scale, or accept/reject of VEX statements).

   The novelty is real-company data, adding JS/npm (missing in VEX-Bench), and developer-validated labels.
2. **Secret detection quality study.** Run Gitleaks + TruffleHog (with verification) + detect-secrets over company repos and full git history, deduplicate by fingerprint, then add an LLM false-positive filter. Measure precision (labeling every candidate is feasible), recall estimated through seeded canaries or a union-of-tools pseudo-oracle, time to remediate (rotate/revoke), and the false-positive reduction from the LLM. This is lower risk, and labeling is cheap.
3. **Security regression gate.** Add one of the above as a CI gate, with VEX/allowlist baselines so that only new reachable or new verified findings fail builds. Measure the build-failure rate before and after.

Risks:
- With 3 weeks and 7 people, the labeled sample will be small; report confidence intervals.
- LLMs can suppress true positives (the "Sifting the Noise" caveat), so recall must be reported, not just reduction.
- Sending company code or secrets to external LLM APIs may be prohibited. Prefer local open models, e.g., the DeepSeek/GLM-class models in VEX-Bench, or redact secret values before sending candidates.

### Gaps
- I found no published study that measures time-to-remediate or developer acceptance of reachability-filtered SCA alerts in an industrial setting after 2022. Ponta et al. 2020 at SAP is the closest, and it is pre-2022.
- No public npm/JS exploitability ground-truth benchmark was found.

## Q4. Practical tool details: free/open-source reachability support for Java, JS, Python and Go

### Takeaway
Free, production-quality reachability currently means Go only: govulncheck, also wrapped by OSV-Scanner `--call-analysis=go`, which is on by default. OSV-Scanner's Rust and JAR call analysis is experimental. Semgrep Supply Chain's reachability (Java, JS/TS, Python, Go and more) is a commercial product. Eclipse Steady (Java) is open source but old. For Python and JS, no mature open-source reachability tool was confirmed.

### Cited Findings
- OSV-Scanner v2:
  - `--call-analysis=<lang|all>` and `--no-call-analysis=<lang|all>`, with Go analysis enabled by default.
  - The Go analysis uses the golang.org/x/vuln/scan package (govulncheck) and needs the Go toolchain on PATH.
  - Rust analysis is experimental: it compiles the project and reads DWARF debug info, and it runs dependency `build.rs` scripts, which can execute arbitrary code.
  - `all` also enables the experimental Rust and JAR analyzers.
  - The v1 docs used `--experimental-call-analysis`.
  - [OSV-Scanner source scanning docs](https://google.github.io/osv-scanner/usage/scan-source); [OSV-Scanner v1 usage](https://google.github.io/osv-scanner-v1/usage/)
- govulncheck analyzes function-pointer and interface calls conservatively, so it may produce false positives or inaccurate call stacks. — [govulncheck doc.go](https://go.googlesource.com/vuln/+/v1.1.0/cmd/govulncheck/doc.go)
- In VEX-Bench, govulncheck completed only 19 of 30 Go cases (precision 22.2%, recall 28.6%). OSV-Scanner reachability raised Go precision only from 24.1% to 28.6%. — [arXiv 2609.08040](https://arxiv.org/html/2609.08040)
- Semgrep Supply Chain, a commercial product, has reachability for C#, Go, Java, JavaScript/TypeScript, Kotlin, Python, Ruby, Scala, Swift and PHP. Rust gets version matching only, and Dart and Elixir are unsupported. Lockfile-less scanning is in beta for C#, Java, Kotlin, Python and Ruby. — [Semgrep SC feature support](https://semgrep.dev/docs/semgrep-supply-chain/sca-feature-support)
- Eclipse Steady covers Java (Maven/Gradle) with static and dynamic (test-based) reachability under Apache-2.0. It was originally SAP Vulas and open-sourced in 2018. — [GitHub](https://github.com/eclipse-steady/steady)
- Secret tools for CI: Gitleaks (high recall, low precision per ESEM 2023), TruffleHog (52% recall in ESEM 2023; the verification feature is recommended), and GitHub secret scanning (75% precision). — [arXiv 2307.00714](https://arxiv.org/abs/2307.00714)

### Inferences
- For a multi-language company stack, a pragmatic open-source pipeline is: Syft SBOM; Grype + OSV-Scanner (+ Trivy) for matching; govulncheck for Go reachability; for Java, either Eclipse Steady (if it still builds) or a lightweight "is the vulnerable symbol imported or called" grep/Semgrep-CE rule built from fix-commit symbols. In every case, add an LLM agent stage with a VEX-Bench-style prompt for the final judgment.
- Do not treat "no call found" as proof of non-exploitability. The OSV docs and VEX-Bench both warn against it, so output should be "not_affected (code_not_reachable)" with evidence, subject to human sign-off.

### Gaps
- Endor Labs, Snyk reachability and GitHub Dependabot reachability: languages, pricing tiers and accuracy were not verified.
- I did not verify whether free OSS tools such as Jelly (JS call graphs), PyCG (Python call graphs) or the Rust cargo ecosystem can be readily used for SCA reachability. They are known research call-graph tools, but this was not checked in this session.
- The current exact OSV-Scanner JAR call-analysis capability is not verified beyond "experimental".
